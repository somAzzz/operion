## 4. 本次新增发现

### R01：事实值存在，并不表示属于当前对象（P0 / I02）

以下探针直接调用 `verify_business_answer(tool_calls, answer)`，工具结果均为 `ok=True`，没有使用模型：

| 合成工具事实 | 错误答案 | 实际结果 / 应有结果 |
|---|---|---|
| get_sales_order：订单 1，USD 177.60，Draft | 订单 1 金额 EUR 177.60，状态 Draft | ALLOW / 拒绝；相同数字的币种被改写 |
| 两次 get_customer_overview：客户 1 有 0 单，客户 2 有 3 单 | 客户 1 有 3 单，客户 2 有 0 单 | ALLOW / 拒绝；数量归属互换 |
| 两次 get_sales_order：订单 1 EUR 100 Draft；订单 2 EUR 200 Completed | 订单 1 EUR 200 Completed；订单 2 EUR 100 Draft | ALLOW / 拒绝；金额和状态归属互换 |

实际对象 ID 使用 `wwi:sales_order:1/2`、`wwi:organization:customer:1/2`。首个币种反例同时传入 `grade_case({"tool":"get_sales_order"}, calls, answer)`，返回空失败列表。它说明该评分路径同样漏判，并非声称所有配置的 gold 都必然漏判。

原因是部分校验把成功工具结果的数量、金额、状态汇总为集合，检查值是否出现，未充分绑定对象、字段和币种。金额解析也未保留币种语义。这些是合成反例，不是实际用户事故。

改进：建立 `(entity_id, field, value, currency/uom, source, observed_at, evidence_pointer)` 事实合同。先让结构化答案或确定性事实卡绑定证据，再生成受约束说明；无法确定归属的关键声明不应标为 FACTS_SUPPORTED。避免仅不断增加正则表达式。

验收：三个反例永久回归；正确多对象回答、币种正确的相同金额、正常改写均通过；补充字段混淆、否定句、部分数据和跨轮旧事实。gold 用人工审核常量/独立核对数据，不复用运行时解析器生成预期；未知解析覆盖明确记为未验证。

### R02：offline 入口可能继承破坏性数据库配置（P0 / I16）

静态检查发现 `scripts/verify.sh offline` 未移除 `OPERION_TEST_ACTION_DATABASE_URL`。测试发现流程包含执行 `DROP SCHEMA public CASCADE` 的 Action 测试；若调用者继承该变量，所谓 offline 可能触达数据库。CI 已显式移除变量，但本地脚本没有同样保护。本次使用上面的安全命令，未执行破坏性探针。

`scripts/test_postgres.py` 只验证数据库名以 `_test` 结尾，不负责创建隔离数据库；后缀不能证明其可销毁。新增 runner 管理的临时实例/数据库、唯一运行标识及限定账号，清理前确认归属。直接运行测试也应拒绝无隔离证明的目标。验收包含继承 DSN 的 offline 仍不连接数据库、错误目标拒绝及隔离库完整执行/清理。

### R03：观察到 trace 还不等于开发者能快速复现（P1 / I15）

现有脚本覆盖构建、单测、专项评测，尚缺一个 case ID 贯穿 domain→真实 stdio MCP→脚本模型→真实模型→Web 的入口，以及统一 expected/actual 差异、失败层和重跑命令。Langfuse 默认不采集内容有利于保护数据，但调试仍需要独立、显式授权且脱敏的本地内容证据。

此外，最终文本改为缓存后，首个 SSE 事件不代表用户看到首个已验证答案。补充首次已验证文本延迟、误拒绝率、门禁漏判率和各层耗时。取消路径的缓存文本/历史持久化及后续恢复需专项测试；目前只列待验证项，不认定已经复现泄露。

## 6. 业务功能与面试交付是否还需要扩展

基础设施进步没有自动填补 ERP/CRM 业务范围。仍缺少端到端经营证据：销售后续交付/退货/应收，采购到货/应付，库存与预留，CRM 商机阶段/活动/跟进结果，跨系统权威来源及增量变更处理。这里指 Operion 的集成和验收范围，不是说 ERPNext/Twenty 产品没有这些功能。

个人项目优先选择一个闭环，例如“客户订单异常识别→解释冲突与证据→人工批准内部跟进→回读结果”，使用现有受控 Task 能力并遵守既有写入准入。先证明一个闭环，不同时开放发票、付款、库存调整和对外通知。当前 scope 不足以声称完整 ERP/CRM。

面试需要交付：可复现启动步骤、系统边界图、脱敏 golden cases、一次失败到修复的证据差异、正常/越权/上游故障三段演示，以及一页明确列出测试桩、真实依赖与生产未验证项。优先把现有能力讲清楚，新增功能仅以业务闭环需要为准。
